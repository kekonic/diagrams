# Comparing layouts

Automatic layout still requires editorial selection. Compare a small set of credible policies
instead of accepting the first successful render or randomly turning knobs.

## Make a few alternatives

Keep nodes, edges, labels, kinds, styles, and meaningful boundaries fixed. Choose two to four
alternatives that reflect genuinely different ways to read the diagram:

- `LR` for a pipeline or request path and `TD` for stages, hierarchy, or a diagram used in a document;
- `stack` versus `row` for a real peer region;
- one ungrouped baseline versus meaningful visible or chromeless regions;
- normal versus compact density only when the intended display size can preserve legibility.

Change one layout idea at a time. Do not try every possible option, add arbitrary coordinates, or
change what the diagram says to make one alternative win.

## Inspect at the destination size

Render every alternative with the same theme, font, and export settings. Inspect the
actual image at the width where readers will see it. Compare:

1. immediate entry point and reading order;
2. whether the main idea is easy to find;
3. peer alignment and meaningful region shape;
4. crossings, backtracking, long edge spans, and labels detached from their relationships;
5. effective text size and unnecessary node width;
6. whitespace balance and aspect ratio;
7. whether side actors and external systems remain visibly secondary;
8. whether any boundary becomes a giant or misleading enclosure.

Do not optimize one metric in isolation. A compact diagram with tangled edges is worse than a
slightly larger diagram with a clear story. Record a one-sentence reason for rejecting each losing
alternative and deliver only the selected source and matching output files.

If every sensible alternative is poor, fix the grouping or split the diagram. Do not keep tuning spacing
around a graph that contains multiple competing stories.
